Identity and access

Passwords use salted scrypt hashes. The backend issues a custom HMAC-SHA256 signed bearer token with a seven-day expiry. Google and Facebook sign-in are available when configured.

Server checks enforce account roles, ownership and conversation membership. Socket connections also validate their token.

Request protection

Helmet security headers, an origin allowlist, endpoint rate limits and input validation protect the API boundary. JSON requests are limited to 100 KB.

Image uploads accept JPEG, PNG and WebP, up to 5 MB per file. Payment proof access is limited to the order's buyer and supplier.

Inventory consistency

Pending orders do not reserve stock. Supplier confirmation decrements stock and changes order status atomically. Cancelling a confirmed order restores stock. Repeating the same status change does not deduct stock again.

Storage boundaries

Public-facing image URLs refer to Cloudinary. Payment receipts remain in MongoDB, excluded from normal order JSON and normal projections. Tracking positions are stored separately from order documents.

Runtime flows & deployment

From checkout to delivery

1 · Place order
Buyer submits quantity, delivery details and COD or GCash payment information.
→
2 · Review payment
For GCash, supplier checks the receipt and funds, then approves or rejects.
→
3 · Confirm
Supplier confirms; the database transaction deducts stock and updates the order.
→
4 · Track & finish
Supplier shares device GPS, buyer views updates, supplier completes the order.

Communication and tracking

  • Chat: messages are submitted through REST, persisted in MongoDB, then emitted to the authorized conversation room.
  • Location: supplier browser GPS is uploaded through the order location endpoint, stored as TrackingPoint records, and broadcast to buyer/supplier rooms.
  • Refresh: GPS uploads are throttled to once per ten seconds per open order. Tracking also refreshes every thirty seconds and on reconnect.
  • Tracking ID: CD- followed by the order ID. Lookup requires an authenticated order participant.

Payment behavior

GCash uses manual QR payment and supplier verification. Approval is required before a GCash order can be confirmed or completed. A rejected receipt can be corrected and resubmitted. Payment review and order confirmation are separate actions.

Local development

Vite serves the browser application on port 5173 and proxies /api to the Node API on port 4000. The API runs separately and connects to MongoDB.

Production deployment requirements

  • Serve the Vite build from a frontend host with SPA route fallback; run the Node HTTP/Socket.IO service on a backend host.
  • Set VITE_API_URL to the API origin and CLIENT_ORIGIN to the allowed frontend origin. Enable HTTPS and Socket.IO connectivity.
  • Use MongoDB Atlas or a replica set for order transactions. Keep database, auth, OAuth, SMTP and Cloudinary secrets in the backend environment.

This is the deployment shape supported by the code. An actual production host or running deployment was not verified.

Operational boundaries: GCash is not connected to a payment gateway. Delivery tracking requires the supplier's page to remain open and the device awake; it is foreground browser GPS. Presence and default rate-limit state are in-process; a multi-instance deployment would need shared coordination.
